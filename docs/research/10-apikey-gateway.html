heron-connect API Key 网关设计 对标 one-api

目标：让 heron-connect 不只是"消费"服务商凭据，还能"提供"服务——像 one-api 一样签发 API Key，供其他工具 / CLI / 团队成员复用本机已配置的模型服务。

1. 要解决的问题

当前 heron-connect 的 Provider 是单机凭据切换器：key 只能注入本机 CLI 子进程的环境变量。但实际场景中经常有第二消费方：

  • 其他机器上的 Claude Code / Codex 想复用这家中转站的 key，但 key 不想到处复制；
  • 脚本、Cherry Studio、沉浸式翻译等 OpenAI 兼容客户端想接同一个上游；
  • 团队内想共享一组上游渠道，但不公开真实 key，并能随时吊销。

one-api 的解法是自建网关 + 令牌体系：客户端持有 heron 签发的 key（sk-heron-...），真实上游 key 永不出网关。

2. 总体架构

消费方任意 OpenAI / Anthropic 兼容客户端
→
heron-connect 网关验证 sk-heron-* key
选择 active Provider / 指定渠道
→
上游服务商中转站 / SiliconFlow / 官方 API

核心思路：在 heron-connect 内嵌一个 HTTP 服务（可复用现有 web 服务端口或独立端口），对外暴露 OpenAI 兼容接口（/v1/chat/completions、/v1/models，可选 Anthropic 的 /v1/messages），请求进来后用配置的 Provider 凭据转发到真实上游，流式 SSE 透传（本地 provider proxy 已有现成的 SSE 透传实现，proxy/provider_proxy.go）。

3. API Key 生命周期

3.1 创建

# CLI
heron-connect key add --name "laptop-claude" --expires 90d --scope chat

# 或聊天内
/key add laptop-claude

# 或 Web 页面（新增 Keys Tab）
POST /api/keys  { "name": "laptop-claude", "expires_in_days": 90 }

服务端生成 sk-heron-<随机 32 字节>，仅创建响应时返回一次明文，库中只存 SHA-256 哈希（与 Provider key 的脱敏展示策略一致）。

3.2 使用

# 任何 OpenAI 兼容客户端
export OPENAI_BASE_URL=http://nas.local:8317/v1
export OPENAI_API_KEY=sk-heron-xxxxxxxx

curl $OPENAI_BASE_URL/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{ "model": "claude-sonnet-4-6", "messages": [...] }'
# 远程机器上的 Claude Code（相当于把 active provider"分享"出去）
ANTHROPIC_BASE_URL=http://nas.local:8317 \
ANTHROPIC_AUTH_TOKEN=sk-heron-xxxxxxxx \
  claude

3.3 管理

操作方式说明
吊销/key revoke <name> / Web 按钮立即失效，真实上游 key 不受影响
轮换创建新 key + 吊销旧 keyP1 再考虑 key 平滑轮换窗口
查看用量Keys Tab 每行显示调用次数 / token 数复用 UsageReport 采集管道，按 key 维度记一笔
过期创建时可选 --expires校验时惰性判断即可，无需定时任务

4. 请求处理流程

① 接收请求解析 Authorization Bearer
→
② 鉴权hash 比对 / 过期检查 / 吊销检查
→
③ 选渠道默认 active Provider
模型名 → Provider 路由
→
④ 改写转发替换为真实 key + 上游 baseURL
SSE 流式透传
→
⑤ 记账按 key 记用量
(次数 / tokens)

其中 ③ 是与 one-api 拉开复杂度的地方——heron 实际场景同一时刻基本只用一个服务商，因此不做按模型分流的路由表：默认走当前 active Provider，模型名原样透传。合理的是自动切换：当 active Provider 持续失败（429 / 断连 / 鉴权失效）时，自动切换到下一个可用的 [[providers]]，并在会话流 / Web 上提示"已自动切换到 XX"。这正好也补齐了现有聊天链路没有故障转移的短板。

5. 配置示意（config.toml）

[gateway]
enabled  = true
port     = 8317          # 默认独立于 web 端口
bind     = "0.0.0.0"     # 局域网共享才开放；默认 127.0.0.1
allow_models = ["claude-sonnet-4-6", "gpt-5-codex"]  # 可选白名单

[[gateway.keys]]
name    = "laptop-claude"
hash    = "sha256:..."    # 明文不落盘
created = 2026-10-16
expires = 2027-01-14
scope   = "chat"

6. 安全要点

  • key 只存哈希，创建响应一次性返回明文；
  • 默认只绑 127.0.0.1，开启局域网共享时在 Web 上醒目提示并建议走 Tailscale / 反代 TLS；
  • 真实上游 key 永不回传：错误信息统一脱敏（沿用现有 user_visible_error 元数据约定，内部错误不透出上游地址与 key）；
  • 限速：复用现有 rate_limit 思路，按 key 做简单令牌桶，防脚本失控刷爆上游；
  • 审计：每次调用记 key 名 + 模型 + token 数，落 UsageReport，方便发现异常消耗。

8. 分期实施建议

  • P1 — MVP：网关服务 + 单渠道（active provider）转发 + key 增删查（哈希存储）+ Web Keys Tab。只支持 /v1/chat/completions 与 SSE。
  • P2 — 自动切换：active Provider 连续失败时自动 failover 到其他 [[providers]]（可配开关与顺序），切换事件进会话流告警 + UsageReport 记录；/v1/models 按 active provider 返回、按 key 限速。
  • P3 — 增强：切换恢复（原渠道恢复后切回）、key 分组/配额、Anthropic 原生格式端点（供 Claude Code 直连零改写）、key 轮换窗口。
边界提醒：做 P1 就够解决"创建一个 key 其他地方用"的诉求。不要一开始就把 one-api 的计费、多用户、渠道池搬进来——heron-connect 是单用户自托管工具，P1 + P2 已覆盖 90% 场景。
