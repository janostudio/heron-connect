# UX 差距根因分析

> 按用户体验影响从高到低排序

## P0 — Engine God Object（可维护性危机）

### 现象

`core/engine.go` 是 **13,820 行**的单体文件，包含 200+ 个 `func (e *Engine)` 方法，涵盖：
- 消息路由和分发
- 所有 `/command` 处理（30+个命令）
- 流式事件循环
- 卡片渲染（15+ 种卡片类型）
- 工作区管理
- Cron 执行
- Bot-to-Bot Relay
- 权限检查
- 配置持久化回调

### 根因

初始设计时以 `Engine` 为核心结构是合理的，但随着功能增加，所有代码都堆到同一个文件中，从未做过结构性的模块化。

### 影响

1. **直接影响迭代速度**：添加任何功能都需要在 13k 行中找对应位置，极易引入错误
2. **测试难度指数增长**：`engine_test.go` 也有 12k 行，stub 设置复杂
3. **新平台接入困难**：不清楚需要实现哪些接口组合才能获得正确行为
4. **流式 bug 难排查**：流式逻辑散落在事件循环各处，状态变量众多

### 量化影响

```
一个简单的命令修改（如 /alias）：
  - 需要阅读 engine.go 中的 cmdAlias, cmdAliasList, cmdAliasAdd, cmdAliasDel（~100行）
  - 需要理解 SessionManager、interactiveStates 的上下文
  - 需要查找 i18n key
  - 需要更新 renderAliasCard
  
  实际修改：10 行
  需要理解的上下文：1000+ 行
```

## P1 — 流式体验碎片化

### 现象

用户在不同平台上的流式体验差异很大：
- Feishu：有 RichCard，进度可见，工具步骤可见
- Telegram：有 UpdateMessage，但只是文字逐渐增长
- Discord：有 UpdateMessage + 删除预览策略
- DingTalk：有 AI Card（StreamingCard），专用接口
- WeChat Work/LINE：无流式，等全量完成
- QQBot：无流式，等全量完成

问题不在于各平台能力不同（这是客观限制），而在于：
1. **没有统一的降级策略**：`degraded` 标志的处理逻辑散落各处
2. **Mode × 平台能力的组合空间无文档**：用户选 `stream` 模式 + 某平台会发生什么？
3. **stream 模式和 streamPreview 机制独立**：两套系统有复杂的互相影响

### 根因

历史演化导致的：
- 最初只有 `quiet/full` 两种 mode
- 后来加了 `compact`（进度卡片）
- 后来加了 `stream`（流式预览）
- 每次加都是打补丁，没有统一抽象

### 用户可感知的 bug 场景

```
场景1：Telegram + stream 模式
  - 用户发消息
  - 看到消息逐渐更新（好）
  - 但如果 Agent 用了很多工具，每次工具调用都 freeze/discard 预览
  - 最终收到多条消息，而不是一条完整回复
  - 用户困惑：为什么会这样？

场景2：飞书 + full 模式
  - Agent 每次工具调用都发一条消息
  - 一个复杂任务可能发出 20+ 条消息
  - 用户的消息列表被刷屏
  
场景3：长代码块 + 任何平台
  - Agent 输出 500 行 Python 代码
  - 4000 字符截断将代码块切成两段
  - 第一段没有关闭 ``` 标记，渲染失败
```

### 影响评级：高

直接影响用户每次与 Agent 的交互体验。

## P1 — Markdown 感知分块缺失

### 现象

当 Agent 响应超过 `maxPlatformMessageLen = 4000` 字符时（对于代码任务这很常见），消息会在第 4000 个字符处硬截断。

### 根因

`core/markdown.go` 只有 `StripMarkdown` 函数（用于不支持 Markdown 的平台），没有 `ChunkMarkdown` 函数。

### 具体问题

**代码块截断（最常见）：**
```
输入（5000字符的代码解释）:
  分析：...（500字符）
  ```python
  def solve():
      # 200行代码...（4000字符）
  ```
  总结：...（500字符）

截断结果（4000字符处）：
  消息1: 分析：...（500字符）\n```python\ndef solve():\n    # 100行代码...
  消息2（如果有的话）: 剩余100行代码...\n```\n总结：...

问题：消息1 的代码块没有关闭，Markdown 渲染器会把整个后续内容都当作代码
```

**表格截断：**
```
输入（表格超过4000字符）:
  | 列1 | 列2 | 列3 |
  |-----|-----|-----|
  | ... 很多行 |

截断结果：
  消息1: 前4000字符（可能截在某行中间）
  
问题：截断的表格无法渲染，显示为乱码
```

### 对比 OpenClaw 的处理

OpenClaw 的 `chunkMarkdownText` 会：
1. 优先在 `\n\n` 处分块
2. 其次在列表项处分块
3. 保证不在代码块内截断
4. 保证不在表格行内截断
5. 只有在找不到合适分割点时才硬截断

### 影响评级：高

代码类任务（最常见的 AI 编码 Agent 用途）几乎必然触发此问题。

## P2 — 平台原生富格式利用不足

### 现象

飞书、DingTalk 等平台支持丰富的原生消息格式，但当前实现利用不完整：

**飞书（Feishu）：**
- 支持 Interactive Card（交互式卡片），有按钮、进度、状态等
- CC-Connect-QHN 已实现 `RichCardSupporter` 接口，但只在部分场景使用
- 代码块在飞书 Lark Markdown 中有特殊渲染，但转换不总是正确

**DingTalk：**
- 支持 AI Card（流式进度卡片），专用于 AI 对话场景
- CC-Connect-QHN 有 `StreamingCardPlatform` 接口，已实现
- 但 tool steps 的展示不如 OpenClaw 丰富

**Slack：**
- 支持 Block Kit（复杂结构化布局）
- CC-Connect-QHN 只发普通 Markdown（`markdown_slack.go` 做了方言转换）
- 没有使用 Block Kit 展示工具进度

### 根因

- 每个平台能力由不同开发者在不同时间实现，没有统一的"如何充分利用平台能力"指南
- 接口定义（`core/interfaces.go`）已经有足够的抽象，但集成没有被全面推进
- 测试平台能力集成需要有对应平台的测试账号，门槛高

### 影响评级：中

影响"有平台原生能力"用户的体验提升，但不影响基本功能。

## P2 — 入站消息上下文单薄

### 现象

AI 处理消息时缺乏关键上下文：

1. **不知道当前平台是什么**：AI 可能输出 Telegram HTML 格式的文本，但用户在飞书
2. **不知道平台支持什么格式**：AI 输出 Markdown 表格，但平台是 WeChat Work（不支持）
3. **没有历史感知**：每次对话相对孤立（除非 Agent 本身维护 session history）
4. **不知道用户身份**：在群组聊天中，AI 不知道哪个用户是管理员、哪个是普通成员

### 已有的部分解决方案

`FormattingInstructionProvider` 接口已存在，部分平台实现了：
```go
// 如果平台实现了 FormattingInstructionProvider
// engine 会调用 SetPlatformPrompt 将格式化指令注入 agent
type FormattingInstructionProvider interface {
    FormattingInstructions() string
}
```

但仅限于格式化指令，没有历史、用户角色等上下文。

### 影响评级：中

影响 AI 回复质量，特别是格式和内容的准确性。

## P3 — 多账号支持缺失

### 现象

每种平台类型只能配置一个账号实例。

### 场景

- 工作用飞书机器人 + 个人用飞书机器人，需要两个 cc-connect 实例
- 同一 Agent 服务多个 Telegram 群组，但 allow_from 设置不同

### 现有的部分解决方案

多工作区（`multiWorkspace`）功能可以让一个机器人管理多个项目，但这是"一对多工作区"，不是"多账号"。

### 影响评级：低

需要多账号的场景相对少见，可以通过运行多个 cc-connect 进程解决。

## 总结：优先级 × 改进收益矩阵

```
         高收益                          低收益
高优先级  ┌─────────────────────────┐    ┌─────────────────┐
         │ Engine 拆分             │    │ 多账号支持      │
         │ 流式体验统一            │    │                 │
         │ Markdown 感知分块       │    │                 │
         └─────────────────────────┘    └─────────────────┘
低优先级  ┌─────────────────────────┐    ┌─────────────────┐
         │ 平台原生富格式          │    │ 性能优化        │
         │ 入站上下文增强          │    │                 │
         └─────────────────────────┘    └─────────────────┘
```

**建议执行顺序：**
1. Engine 拆分（解锁后续所有改进的先决条件）
2. Markdown 感知分块（独立模块，低风险，高收益）
3. 流式体验统一（需要 Engine 拆分后才能干净实现）
4. 入站上下文增强（在新的 Pipeline 架构下实现）
5. 平台原生富格式（各平台按需推进）
